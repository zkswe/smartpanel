# 屏保视频「卡帧 / 黑屏很久 / 声音先出 / 没声音」排查报告

日期：2026-10-01 · 设备：192.168.101.2:5555（Z20 / SSD202D，EasyUI 2.2.0，FlyThings V2.1）
钟工反馈的四个现象，**四个互不相同的根因**，都已定位、修复并真机验证。

---

## 一、结论速览

| 现象 | 根因 | 处置（已落地） |
| --- | --- | --- |
| **卡帧**（我转的素材卡、微信上传的流畅） | **素材带 B 帧** → 本机 VDEC 输出口用户深度只有 1 个 buffer，进 DPB 重排序就饿死 → 上屏从 24 fps 掉到 **12 fps** | 素材**禁 B 帧**（`-bf 0 -b_strategy 0`）；`media_gate.py` 已设为默认 |
| **起播黑屏很久 / 播放时长在 0.2~11 s 乱跳** | 屏保给 `SimplePlayer` 开了 `setSynchronizing(true)`（= "对基准钟播放"） | 只拼墙时开：`wantSynchronizing()`，prefs `sp_ss_sync` 可覆盖 |
| **声音比画面早 / 人在设置页也在放声音** | 屏保页**隐藏时**其 1 s 心跳仍在跑，素材一变就 `refreshListIfChanged()` → `playItem()` 在后台把视频+声音又起一遍 | `sSsVisible` 守卫（三道起播入口全判"屏保是否在前台"） |
| **新素材完全没声音** | 素材只有 mp4；固件 `libzkmedia.so` 只注册 Mp3/Wav 解析器，**解不了 mp4 里的 AAC** → 屏保声音必须配**同名 mp3** | 抽同名 mp3 配对（新增 `media_gate.py --audio-only`） |

> ★ 一处**更正**：本篇早期版本把"卡帧"记成**帧率**所致。2026-10-01 的真机 A/B 推翻了该结论 ——
> **帧率不是原因，B 帧才是**。钟工后来的 50/60 fps 高码率原片（零 B 帧）他验收"流畅"，
> 且明确**不要压缩码率的版本**，因此这批原片一个字节都没重编。

## 二、卡帧真凶 = **B 帧**（同一台机、同一条链路的 A/B 实测）

拿钟工微信上传、他说"没问题"的那条当**基准**，与我的转码版逐项比：

| | 微信上传（流畅，基准） | 我的转码版（非常卡） |
| --- | --- | --- |
| **B 帧** | **`has_b_frames=0`** | **`has_b_frames=2`** |
| 帧类型分布 | **I=10 / P=230，零 B 帧** | B=144 / I=6 / P=90 |
| SPS | `pic_order_cnt_type=2`、ref≈1 | `pic_order_cnt_type=0`、ref 3~7 |
| 其余（编码/分辨率/码率/profile/faststart/AAC） | H.264 High@L3.0 · 480×480 · 735/810 kb/s | **完全一样** |

在设备上直接量上屏帧率（`mi_vdec0` 的 `FinishCnt` / `RealDstFrmrate`、`mi_disp0` 的 `RecvBufCnt`）：

| 素材 | 实际上屏帧率 |
| --- | --- |
| 微信上传那条（零 B 帧） | `RecvBufCnt` 每秒 **+24** → **满帧** |
| 我上一版（带 B 帧） | `FinishCnt` 每秒 **+12** → **只有一半**（肉眼"非常卡"） |
| 重编后（零 B 帧） | `FinishCnt 691→1106 = +24/s`，`RealDstFrmrate 24.01` → **满帧** |

**机理**：B 帧要求解码器先进 DPB 重排序再出帧，而本机这条链路
`src/wall/mi_h264_player_port.cpp` 的 VDEC 输出口**用户深度只有 1 个 buffer**（实测 `usrDepth 1 / BufCntQuota 2`），
一重排就饿死 → 稳定掉一半帧。**零 B 帧时解码顺序 = 显示顺序，不需要重排。**

> 顺带修正一个次要结论：上屏链路有 **~24 fps 上限**。>24 fps 的源会丢帧，但**观感可接受**
> （钟工的 60 fps 白噪音片验收"流畅"）——**不要为了帧率去重编已经确认过画质的原片**。

## 三、起播黑屏久 / 时长乱跳 = `setSynchronizing(true)`（反汇编定位）

`src/wall/WallPlayer.cpp::run()` 原来无条件 `sp.setSynchronizing(true)`。
对 `libsimple-player.a` 反汇编（`arm-pc-linux-gnueabihf-objdump -d --demangle`）得到的语义 = **"对基准钟播放"**：

```
phase  = standardTime() % (duration + parseTime) - parseTime
target = standardTime() - phase
每包：等 standardTime() >= accum_pts + target 才送 (H264Player::stream)
收尾：等 standardTime() >= duration + target 才从 play() 返回
→ play() 返回时长 = duration + parseTime - (standardTime_start mod T)
   即"播到绝对钟的下一个整点"（T = duration + parseTime）
```

机制与现象一一对应：

| 机制 | 现象 |
| --- | --- |
| 起播时把 `phase` 对应的**前若干秒画面一次性灌进解码器**（这些包的到期时刻已过去） | **卡帧 / 跳帧** |
| 灌流把 MI DISP 喂不上（起播后 5~11 s `mi_disp0 RecvBufCnt` 仍为 0，`mi_vdec0` 一度整个 proc 消失） | **黑屏很久** |
| 声音走**独立播放器**（`src/logic/ss_audio.cc`），不受相位影响，从 0 正常播 | **声音先出** |

实测证据：海滩浪花那条 `play` 记于 20:42:29.246，`mi_disp0 RecvBufCnt` 直到 **20:42:36.93** 才从 0 变 8 → 起播 **7.5 s 一帧未出**。

**修法**：

```cpp
// src/wall/WallPlayer.cpp —— 屏保不拼墙就不该对齐基准钟；视频墙的整边界对齐才需要
static bool wantSynchronizing() {
    const int ov = StoragePreferences::getInt("sp_ss_sync", -1);   // -1 自动 / 0 强制关 / 1 强制开
    if (ov == 0) return false;
    if (ov == 1) return true;
    return WallLink::getInstance()->enabled();
}
sp.setSynchronizing(wantSynchronizing());
```

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| `play()` 时长 | **0.2 s ~ 11.0 s 随机漂移**，且"短播"会换素材 | **每条精确 10.07 ~ 10.09 s** |
| 起播出首帧 | 5 ~ 11 s 后（`RecvBufCnt` 恒 0） | **换片即开始收帧** |
| 日志 | `sync=1` | `sync=0 (屏保：按 PTS 正常起播)` |

## 四、音画同步 + 「人在别的页面也在放声音」

### 4.1 起播时的音画对齐（解决"声音比画面早"）

视频是**异步**起播（起线程 → 建 H264Parser → MI_VDEC init → DISP enable/bind，约 180~215 ms 才有第一帧），
mp3 却立刻播 → 声音抢在前面。且 MI 视频层 **77 ms** 就出画，而**屏保页面**（UI 层）画得更慢。

**做法**：`mi_h264_player_port.cpp::stream()` 第一句通知 `WallPlayer::noteFirstFeed()`；
`playItem()` 不再立刻起播 mp3，改挂起；由 **50 ms 心跳 `ssAudioSyncTick()`** 在
**画面已喂流 且 距挂起 ≥ 250 ms**（prefs `sp_ss_async_ms`）时起播；1.5 s 兜底放弃。
单条循环另由 `ssSingleLoopAudioTick()` 每轮重对齐。

实测：**每个切换点 `ss[audio]: sync start …（等到 253 ~ 296 ms）`**；单条循环在 cycle 结束后 ~56 ms 重新对齐。

### 4.2 ★ "人在设置页，声音先跑出来" —— 不是时序问题，是**隐藏页里的清单重建**

日志抓到的现场（修复前）：

```
13:35:00.116  ss[audio]: stop (hide)                  ← 用户点屏离开屏保
13:35:25.597  screensaver audit: 11 个素材全部可播      ← 25s 后，屏保在后台又跑起来了
13:35:25.858  ss[audio]: play …mp3                    ← 人在设置页，声音出来了
```

根因：`refreshListIfChanged()` 由 1 s 心跳推动，**屏保页隐藏时仍在跑**；素材一变（新上传/增删）就
`loadVideoList()` + `playItem(idx, true)` → 在**别的页面上**把视频和声音又起了一遍。

**修法**：`sSsVisible` 守卫 —— `onUI_init/onUI_show` 置真、`onUI_hide/onUI_quit` 置假；
`playItem()`、`ssAudioSyncTick()`、`ssSingleLoopAudioTick()` **三道起播入口全部先判它**。
清单照旧重建（回到屏保就是最新的），只是不再"在后台起播"。

**可复现验证**（用 `bin_tools/z20/touch` 注入触摸，本板 `ft5x_ts` 是单点协议 →
`touch --proto single -d /dev/input/event0 tap 240 400`）：

```
14:19:08.862  screensaver touch -> homeActivity
14:19:09.055  ss[audio]: stop (hide)
14:19:20.773  screensaver audit: 10 个素材全部可播
14:19:20.781  screensaver list refreshed -> 9 items (idx=8)
14:19:20.781  screensaver playItem 忽略（屏保不在前台）idx=8     ← 拦住了
14:19:25.758  screensaver list refreshed -> 5 items (idx=0)
14:19:25.758  screensaver playItem 忽略（屏保不在前台）idx=0     ← 拦住了
…（每 5 s 一轮，全部只有"忽略"，无一次起播）
14:19:50.294  home: idle -> screensaver                        ← 自动回屏保才真正起播
14:19:50.620  ss[audio]: sync start …（等到 278ms，画面已喂流且页面已画）
```

隐藏期间**没有任何** `wall[sp-pkg]: start` / `ss[audio]: play`。

## 五、没声音：素材必须 **mp4 + 同名 mp3 成对**

- 固件 `libzkmedia.so`（34 KB）只注册 **Mp3 / Wav** 解析器 → **mp4 里的 AAC 在设备上解不了**；
  MI 硬解内核那条路也**没有音频代码**。
- 同名规则 = 去掉视频扩展名 + `.mp3`（`ss_audio::trackOf()`）。
- **设备上补不了**（没有 AAC 解码器，也没有 ffmpeg 编码器）→ 必须进机前配对。

新增一条命令（**视频原样不动**，只抽同名 mp3）：

```bash
python tools/media_gate.py --src <素材目录> --audio-only --out <暂存目录>
#   → 输出：N 个 mp4（原样复制）+ N 个同名 mp3
#   抽轨：ffmpeg -vn -c:a libmp3lame -b:a 128k -ar 44100 -ac 2
```

本次实做：10 条 × 161,376 B（128 kbps 立体声 44.1 kHz）。设备日志确认解码正常：

```
D/zkmedia: play: /mnt/sdnand/video/红尾水鸲_10s循环_480x480_H264.mp3
D/zkmedia: mXINGSeeker isValid : 1 · mDuration : 10057 · mFirstFramePos : 45 · mBitRate : 128000 · 2ch 44100
D/zkgui  : ss[audio]: sync start …（等到 278ms）
```

### 5.1 附带抓到：**文件名丢扩展名 → 素材直接从清单里消失**

`烟花绽放_10s循环_480x480_H264.mp4` 传到设备后变成 **`烟花绽放_10s循环_480x480`**（`_H264.mp4` 整段丢了）
→ `*.mp4` 扫不到 → `screensaver audit: 9 个素材全部可播`（少一条）、钟工"这个视频在选择页看不到"。
`mv` 回全名后恢复 `10 个素材全部可播`。这是**投递工具**（资源管理器/同步盘/剪贴板）截断长中文名所致，
不是播放器的韧性问题。
**自查**：`ls /mnt/sdnand/video` 里出现**任何不带 `.mp4` 的行**就是中招；mp3 也要跟着改成修正后的名字。

## 七、关于"要不要报系统团队"

**不需要报 ffmpeg**。视频链路上确实有 SDK 的 ffmpeg（`simple-player` 的 `H264Parser` 用它解封装/拆包），
但它不是本次卡帧/黑屏的原因 —— 原因是我们**主动打开了包自带的"对基准钟"播放模式**（屏保不需要），
以及**素材带 B 帧**（与本机"输出口深度 1"的实现叠加）。
（设备固件 `/lib/libav*.so` 是另一回事：那份是完整 ffmpeg 4.1.3 且解码接到 MI 硬件，属备选路线，与本次问题无关。）

> 唯一**值得反馈给上游**的是产品缺口而非 bug：**小程序/云端上传通道不抽音轨**，
> 素材落进 `/mnt/sdnand/album` 时只有 mp4 → 板上必然静音，而板上无法补救。
> 建议在投递环节补齐同名 mp3（或由面板端约定只接受"mp4+mp3 成对"的素材包）。
