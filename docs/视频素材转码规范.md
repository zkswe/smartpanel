# 视频素材规格与转码规范（Z20 屏保 / 相册 / 视频墙）

> 适用范围：屏保视频（设备 `/mnt/sdnand/video`）、相册素材（`/mnt/sdnand/album`，含小程序上传）、视频墙切片。
> 规格由**播放链路**决定，不是偏好——每条都有真机实测依据（设备 192.168.101.2，EasyUI + MI 硬解内核）。
> 更新 2026-10-01：**设备不解码 H.265**，规格一律在**进机之前**处理掉，由 `tools/media_gate.py` 自动完成。

## 〇、为什么必须在「上传前」处理，不能在设备上补救

| 事实 | 证据 |
| --- | --- |
| 设备播放链路编码类型写死 H.264 | `src/wall/mi_h264_player_port.cpp` 里 `eCodecType = E_MI_VDEC_CODEC_TYPE_H264` |
| H.265 素材实测被拒播 | 设备上留下的 `_t_h265.mp4.bad`（就是被改名隔离的 H265 样片） |
| 设备的 ffmpeg **不能解码** | SDK `ffmpeg` 包 `nm --defined-only libavcodec.a` 只有 `ff_h264_parser`，**没有任何 decoder**；它只做解封装/拆包 |
| 设备侧也没有转码器 | 固件里没有 x264 之类编码器，无 CLI |
| H.265 硬解在本固件里没有出口 | `ZKMediaPlayer(VIDEO)` 实测必报 `media play error`（`libzkmedia.so` 只有 34 KB、只带音频） |

结论：**规格不对的素材进了机器就是死料**。唯一可靠的卡点是**投放到设备之前**。

## 一、一句话流程

```bash
# 素材进机的唯一推荐入口（判定 → 该转的转 → 抽同名 mp3 → 推送）
python tools/media_gate.py --src <素材目录> --mp3 --push --dest /mnt/sdnand/video
```

**确实需要重编时**的口径（禁 B 帧 + 2 s GOP + 码率封顶，2026-10-01 起；**画质已确认的原片不要走这条**）：

```bash
python tools/media_gate.py --src <素材目录> --force --fps 24 --gop 24 --bf 0 --ref 1 \
  --crf 23 --encode-maxrate 1000 --max-duration 10 --mp3 --push --dest /mnt/sdnand/video
```

它做的事：`tools/mp4_probe.js` 读真实规格 → 不达标的按下面参数转码（**达标的原样通过，不重编码**）→ 输出到 `<源>/_ready` → 可选抽 mp3 / 推送。可反复跑（幂等）。

常用变体：

```bash
python tools/media_gate.py --src X --dry-run                 # 只体检，不落盘（先看清单）
python tools/media_gate.py --file a.mp4 --out D:\stage       # 单文件
python tools/media_gate.py --src X --mp3                     # 顺带为带音轨的素材抽同名 mp3
python tools/media_gate.py --src X --max-duration 10 --mp3 --push   # 屏保：截 10s
python tools/media_gate.py --src X --force                   # 达标的也重编
# ★ 画质已人工确认、只缺声音 —— 视频原样不动，只补同名 mp3：
python tools/media_gate.py --src X --audio-only --push --dest /mnt/sdnand/video
```

> ⚠️ **不要为了"看起来更标准"去重编已经确认过的原片**。钟工 2026-10-01 明确：白噪音那批
> 高码率原片（480×480 / 零 B 帧 / 10.008s / AAC 160k）画面效果他满意，**不接受压缩码率的版本**；
> 缺的只是声音，用 `--audio-only` 补 mp3 即可。

## 二、硬性要求（网关自动执行，手工转码照此对齐）

| 项目 | 要求 | 依据 / 为什么 |
| --- | --- | --- |
| 编码 | **H.264 / AVC（`avc1`）——禁止 HEVC/H.265** | MI VDEC 编码类型写死 H264；H.265 实测拒播 |
| **B 帧** | **必须禁用（`-bf 0 -b_strategy 0`）** —— 有 B 帧就卡顿 | ★★ 2026-10-01 现场 A/B 实证：本机 MI 上屏链路吃不下 B 帧的**重排序**。同一段素材，带 B 帧（bframes=3+b_pyramid）实测 **上屏只有 12 帧/秒**（丢一半、肉眼"非常卡"）；改成零 B 帧后 **24 帧/秒**（`mi_vdec0` `RealDstFrmrate 24.01`、`mi_disp0 RecvBufCnt` 每秒 +24）。参考物 = 钟工微信上传的那条：`has_b_frames=0`、`I=10/P=230`、播得很顺。零 B 帧 ⇒ 解码顺序 = 显示顺序，解码器不必先攒进 DPB 重排（我们的 VDEC 输出口用户深度只有 1 个 buffer，一重排就饿死） |
| 参考帧 | **`-refs 1`** | 同上：参考帧多会让这条"输出口深度 1"的链路更容易饿死；参考物也是 ref≈1 |
| Profile / Level | **High**（Main/Baseline 也行），level 交给 x264 自动（480×480 → L3.0） | 设备在播素材全是 `avcC = 01 64 00 1e`(High@L3.0) / `01 64 00 1f`(L3.1) |
| 分辨率 | **屏保：480×480 正方形**；相册：≤480×480 | 高于 480 要实时缩放 → 整片时长在 2~11s 间乱跳、容易提前 EOF |
| 像素格式 | `yuv420p`，SAR/DAR = 1:1（`setsar=1`） | 半平面 420 是 MI VDEC 的输入格式 |
| 帧率 | **不强制**（24/25/30/50/60 都实测可播）；**卡顿的根因是 B 帧，不是帧率** | ★ 更正 2026-10-01：先前把"卡帧"记成高帧率所致，是误判。同一条 60 fps 素材，带 B 帧只有 12 帧/秒（肉眼卡）；去掉 B 帧后 24 帧/秒、钟工验收"流畅"。上屏链路有 ~24 fps 上限（`mi_vdec0 RealDstFrmrate 24.01`），>24 的源会丢帧但**观感可接受**（白噪音/氛围类内容尤其）——不必为了帧率重编。仅当素材是 VFR 时才需要 `-fps_mode cfr` 定住时基 |
| 关键帧间隔 | GOP **≤ 24 帧（1 s @24fps）** | 参考物是每 1s 一个 IDR；起播/坏帧恢复更快，代价可忽略 |
| 视频码率 | **判定门限 ≤1800 kb/s**；转码目标 `-crf 21 -maxrate 1500k -bufsize 3000k` | 门限 1800 = 设备实测硬上限（2006 kb/s 只播 2~3s；1591 kb/s 实测正常播）。x264 的 maxrate 是 VBV 目标、平均会到 ≈1.06 倍，所以门限要留余量 |
| 关键帧 | x264 默认（≈250 帧一个 IDR） | 参考集就是 1~4 个 IDR，循环播放正常 |
| 音频 | 参考规格 = **AAC-LC 44.1 kHz 立体声 128~160 kbps**；屏保声音另配**同名 mp3**（见下） | MI 内核的 simple-player 没有音频代码，音轨在设备上不响 |
| 封装 | MP4 + `-movflags +faststart` | moov 前置，播放器直接吃索引 |
| 时长 | 屏保 10 s；相册保留原片长 | 与现有素材一致 |

### 声音怎么来（两层，互不干扰）

- **画面**：`simple-player` 包（MI VDEC 硬解，H.264）—— 视频轨只喂它。
- **声音**：固件 `ZKAudioPlayer` 播**同名 mp3**（只认 mp3/wav，**解不了 mp4 里的 AAC**）→ `media_gate.py --audio-only --mp3` 就是干这个。
  所以设备目录里 `<视频名>.mp4` 与 `<视频名>.mp3` 要成对存在（同名规则 = 去掉视频扩展名 + `.mp3`，见 `ss_audio::trackOf()`）。
- 一条命令把一整个目录补齐声音（视频一个字节都不动）：
  ```bash
  python tools/media_gate.py --src <素材目录> --audio-only --out <暂存目录>
  # 抽完再推：<暂存>/ 里 10 个 mp4（原样）+ 10 个同名 mp3
  ```

## 三、标准转码命令（手工时用，与网关内部完全一致）

```bash
FFMPEG="D:\Users\zhong\AppData\Local\PC Display Server\ffmpeg.exe"
```

### 1) 屏保素材（1:1 源，10s）

```bash
"$FFMPEG" -i source.mp4 -t 10 \
  -vf "scale=480:480:flags=lanczos,setsar=1" \
  -c:v libx264 -profile:v high -pix_fmt yuv420p -preset medium \
  -crf 21 -maxrate 1500k -bufsize 3000k -fps_mode cfr \
  -c:a aac -b:a 128k -ar 44100 -ac 2 \
  -movflags +faststart -y out_10s循环_480x480_H264.mp4
```

### 2) 非 1:1 源片：先取中心方形再缩放（横屏裁左右、竖屏裁上下）

```bash
# 例：1920x1080 → crop=1080:1080:420:0
"$FFMPEG" -ss 30 -i source.mp4 -t 10 \
  -vf "crop=1080:1080:420:0,scale=480:480:flags=lanczos,setsar=1" \
  ...（编码参数同上）
```

### 3) 相册素材（用户上传：720×720 VFR 是常态，必须显式定帧率）

```bash
"$FFMPEG" -i upload.mp4 \
  -vf "scale=480:480:flags=lanczos,setsar=1" \
  -c:v libx264 -profile:v high -pix_fmt yuv420p -preset medium \
  -crf 21 -maxrate 1500k -bufsize 3000k -fps_mode cfr -r 24 \
  -c:a aac -b:a 128k -ar 44100 -ac 2 \
  -movflags +faststart -y out.mp4
```

### 4) 抽同名 mp3（屏保声音）

```bash
"$FFMPEG" -i out.mp4 -vn -c:a libmp3lame -b:a 128k -ar 44100 -ac 2 -y out.mp3
```

### 5) 参数怎么调

- **码率压不下来**（CRF 21 仍触顶 1500k 且画质崩）：`-crf` 提到 23~24；**不要**上调 `-maxrate` 到 1800 以上。
- **源片 <30fps**（24/25）：保留原帧率，别插帧。**≥30fps**：可保留，也可统一降到 30。
- **VFR 源**：必须带 `-fps_mode cfr`（ffmpeg ≥ 5.1；旧版写 `-vsync cfr`），并显式给 `-r`。
- **不要**加 `-level 4.0` 之类的人为抬级 —— 参考素材是自动档（L3.0/L3.1），抬了无益。
- **视频墙切片**：不用本规范，用 `tools/video_wall/split_wall.py`（额外要求 `-bf 0`、固定 1s GOP、各段编码参数完全一致）。

## 四、禁止清单（每条都是踩过的坑）

1. **HEVC / H.265 / `hvc1`** —— 设备直接拒播；已实测被改名 `.bad` 隔离。**不打算支持 H.265 解码**，一律在上传前转 H.264。
2. **720×720 之类 >480 的分辨率**（小程序上传素材的典型规格）—— 时长 2~11s 乱跳。
3. **>1800 kb/s**（裸 CRF 时复杂画面会飙到 3 Mbps）—— 只播 2~3s 就 EOF。
4. **任何 B 帧（`bframes>0`）** —— ★ 最隐蔽也最致命的一条：编码格式、分辨率、码率、profile/level 全部达标，
   文件也"能播"（不报错、时长达标），**但上屏帧率会掉一半**（实测 24 fps 源只出 12 帧）→ 肉眼就是"非常卡顿"。
   必须 `-bf 0 -b_strategy 0`（`media_gate.py` 已默认如此）。
   ⚠️ 判定方法：`ffprobe -show_entries stream=has_b_frames` 非 0 即中招；
   或看 SPS 的 `pic_order_cnt_type`（=2 通常表示无 B 帧/无重排序）。
   > 这是 2026-10-01 唯一确认的"卡顿"根因。**帧率本身不是问题**（50/60 fps 原片零 B 帧时验收"流畅"），
   > 不要再为了帧率去重编已经确认过的原片。
5. **`-crf 18` 以下 / `-qp 0` 无损** —— 码率失控（见第 3 条）。
6. **指望视频自带音轨出声** —— MI 内核无声，且固件**解不了 AAC**；要声音必须配同名 mp3（走 `ZKAudioPlayer`）。
7. **小程序上传通道不抽音轨**：微信上传到 `/mnt/sdnand/album/*.mp4` 的素材**不会**自动生成同名 mp3 →
   板上静音（`ss_audio::hasTrack()` 为假）。入库走 `media_gate.py --audio-only`，或单独补
   `ffmpeg -i x.mp4 -vn -c:a libmp3lame -b:a 128k -ar 44100 -ac 2 x.mp3`。
   ★ 板上**无法补救**（固件没有 AAC 解码器、也没有 ffmpeg 编码器）→ 必须在进机前配对。
8. **★ 文件名丢扩展名 → 素材直接从清单里消失**（2026-10-01 实际踩到）：
   钟工那批素材里 `烟花绽放_10s循环_480x480_H264.mp4` 传到设备后变成了 `烟花绽放_10s循环_480x480`
   （`_H264.mp4` 整段丢了），于是扫不到它 →
   `screensaver audit: 9 个素材全部可播`（少一条）、用户"这个视频在选择页看不到"。
   ⚠️ 不是韧性问题，是**投递工具**（资源管理器/同步盘/剪贴板）截断长中文名所致。
   **自查**：`ls /mnt/sdnand/video` 里出现任何**不带 `.mp4` 的行**就是中招；`mv` 回全名即可。
   mp3 必须与**改正后**的视频名同名。


## 五、验收（不用肉眼）

```bash
node tools/mp4_probe.js out.mp4                    # 退出码 0、打印 [OK]
node tools/mp4_probe.js <目录>\*.mp4 --max-bitrate 1800
```

判据：`H.264/AVC`、`≤480x480`、视频码率 `≤1800 kb/s`、**`has_b_frames=0`**、`+faststart`；要声音则 `<同名>.mp3` 存在。

设备侧一次看全（素材是否都在、是否成对、有没有丢扩展名的）：

```bash
adb shell "ls /mnt/sdnand/video"      # 每个 .mp4 都该有一个同名 .mp3；有"裸名"文件 = 扩展名丢了
adb shell "logcat -d -s zkgui WallPlayer | grep -E 'audit|sync start'"   # 体检条数 + 音画同步
```

推送到设备（中文名安全：ASCII 暂存名 + 设备侧 `mv`）：

```bash
python tools/push_video.py --src <目录> --dest /mnt/sdnand/video
python tools/push_video.py --src <目录> --dest /mnt/sdnand/video --ext .mp3
```

⚠️ `push_video.py` **推送前会自动体检**（调 `mp4_probe.js`）：不达标的 mp4 一律拦下、退出码 8，并提示先用 `media_gate.py` 处理。
这是第二道防线——即使有人绕过网关直接推，死料也进不了机器。确实要强推用 `--no-check`。
